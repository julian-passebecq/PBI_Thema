## Confirmed findings

### F-01 — P1: Import result reports failure after replacing active state

Location: `theme-forge.html`, `applySpecText` around line 5038; `migrateSpec` around 3454.

Chromium probe: clone the default SPEC, set contractVersion to 999 and report.title to "Future audit candidate", then call applySpecText(JSON.stringify(candidate)).

Observed:
```json
{
  "result": {"ok": false, "msg": "applied, 1 error to look at"},
  "activeVersion": 999,
  "activeTitle": "Future audit candidate"
}
```

A second probe appended a clone of pages[0], producing duplicate identities. Result was `ok: false`, message "applied, 9 errors to look at", while comparing active SPEC against its previous serialization returned unchanged=false.

Cause: the preflight only blocks errors whose display location is spec/pages; version/identity errors pass. SPEC is assigned before the later result computes ok from all content errors. Some errors are deliberately editable, so merely changing all errors to rejection is also the wrong fix.

Decision: use explicit blocking classification and an applied flag. Future versions/duplicate identities reject. Safe incomplete bindings/unsupported kinds can be applied with diagnostics. See ADR-002.

### F-02 — P1: Successful theme import silently converts supplied settings

Location: `parseThemeJson` around 1602 and `buildGeneratedThemeJson` around 1495.

Probe input:
```json
{
  "name": "Theme fidelity probe",
  "dataColors": ["#110000","#220000","#330000","#440000","#550000","#660000","#770000","#880000","#990000","#AA0000"],
  "visualStyles": {"*": {"*": {"title": [{"show": false}]}}}
}
```

Observed apply result: ok=true. Generated export dataColors contained only the first eight values. Generated wildcard title.show was true.

This is broader than the old named-presets defect; the uncommitted named-presets fix is present and its test passes. The current control model performs conversion, but a generic applied message does not tell the user which supplied settings changed.

Decision: Sprint 001 must disclose conversion before acceptance and preserve cancel behavior. Full unedited-theme preservation and precise control ownership belong to S002.

### F-03 — P2: Model validator accepts non-string names

Location: `validateModel` around 6409; `loadModel` around 6426.

Input `{"tables":[{"name":123,"columns":[{"name":456}]}]}` returned an empty validation issue list. Calling loadModel accepted it and replaced MODEL. No exception occurred in this specific probe.

The validator checks truthiness instead of contract types. Do not claim a demonstrated crash; the confirmed problem is accepting structurally invalid metadata into downstream binding logic.

Decision: typed path-aware model validation, consistently enforced before application.

### F-04 — P2: Validator applies reserved-key rules outside known paths

Location: `validateSpec` checkShape around 3563.

Probe: clone a valid spec and set `report.extra = {filters: "a plain extension string"}`.
Observed error: `spec.report.extra.filters must be an array.`

The current recursive key-name classifier treats any property called filters as a contract list, regardless of location. Existing code does not define a complete extension contract, so this is a confirmed behavior and architecture weakness rather than a claim of established upstream compatibility.

Decision: known schema paths are typed; unknown extension data is inert, bounded and covered by preservation/conversion policy.

## Additional source-reviewed risks

### F-05 — P1: Boot discards rejected recovery data

Location: boot around 8076, `clearSession` around 6733, initial render/save scheduling around 8090.

Boot catches restoreSession failure and calls clearSession. Subsequent initial render schedules autosave. The saved original can therefore be removed and replaced by sample state. The regression test currently verifies fallback to a valid sample, not recoverability of the original data.

Evidence level: source inspection, not a fresh raw-storage lifecycle reproduction during this review. Tester must verify the full scenario and update evidence.

Decision: preserve the raw original and suspend overwrite until intentional recovery/reset/replacement.

### F-06 — P2: Input routes do different work

Location: `applySpecText`, `loadSpec`, `loadModel`, `bindContextIO`, `restoreSession`.

Source comparison: file spec loading scrubs/defaults IDs and positions while live spec application follows another path; model/theme/recovery checks differ; theme text lacks the spec text's explicit 4 MiB check. Catching validator exceptions does not make state application atomic.

Evidence level: code inspection; all route combinations were not exercised here.

Decision: share preparation per document type and keep UI-specific behavior in adapters.

## Architecture observations for later lead audit

- History snapshots include theme/spec but not MODEL. A model replacement can change binding context independently of undo state.
- Rendering schedules document history/save, making transaction rollback and stale-draft behavior harder to reason about.
- Theme named-preset preservation is a useful partial fix, not lossless arbitrary-theme support.
- Spec export reports cached specIssues and constructs a selected shape; extension/export preservation and fresh diagnostics require a defined policy.
- Tests use internal globals for several cases. Actual file/drop/full-editor routing and stronger failure assertions are needed.
- Static publish root is the whole repository; later delivery work should publish only runtime artifacts.
- The observed source is too coupled for a casual wholesale source split before input/export contracts are proven.

These are risk/decision inputs, not claims that every corresponding user scenario was reproduced.
